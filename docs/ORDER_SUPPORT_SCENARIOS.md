# 주문 고객지원 시나리오

## 목적

이 문서는 주문 관련 Customer Support Agent가 지원해야 하는 최소한의 고객 관찰 가능 행동을 정의합니다. 이후 Tool, Agent, 다중 턴 대화, E2E 및 Evaluation 작업이 공유하는 행동 계약으로 사용합니다.

시나리오 범위는 주문 상태, 배송 및 취소 가능 여부 문의입니다. 실제 쇼핑몰 전체를 모델링하지 않습니다.

## 문서 해석 원칙

- **Given–When–Then 행동은 규범적 계약입니다.** 후속 구현은 관찰 가능한 결과와 금지 행동을 보존해야 합니다.
- **예시 대화는 비규범적입니다.** 문의 의도를 설명하기 위한 예시이며, prompt, Evaluation 입력 또는 정확한 응답 문구를 고정하지 않습니다.
- **정보원 이름은 개념적인 범주입니다.** 이 문서는 Tool의 인자, 결과 schema 또는 전체 호출 순서를 정의하지 않습니다. 정확한 Tool 이름과 선후관계는 시나리오에서 명시한 경우에만 규범적 계약입니다.
- **고객 컨텍스트는 입력 전제입니다.** 인증과 세션 관리는 이 문서의 범위가 아닙니다.
- **주문 후보는 현재 canonical data에서 검증할 수 있는 사실만 사용합니다.**

## Canonical scenario data

| 주문 | 소유 고객 | 주문 상태 | 배송 상태 |
|---|---|---|---|
| `order-001` | `customer-001` | `processing` | 없음 |
| `order-002` | `customer-001` | `shipped` | `out_for_delivery` |
| `order-003` | `customer-001` | `delivered` | 없음 |
| `order-004` | `customer-002` | `cancelled` | 없음 |

전역 취소 정책은 다음 canonical fact를 제공합니다.

```text
cancellable_statuses = {"processing"}
```

`processing`은 배송사에 인계되기 전 주문 처리 상태를 의미합니다.

## 시나리오 1: 식별된 주문의 상태 문의

### 목적

고객이 주문을 식별한 경우 하나의 주문 정보원을 사용해 근거 있는 답변을 생성하는지 확인합니다.

### Given

- 고객 컨텍스트는 `customer-001`입니다.
- `order-003`은 `customer-001`의 주문입니다.
- `order-003`의 주문 상태는 `delivered`입니다.

### When

고객이 `order-003`의 현재 상태를 문의합니다.

### 필요한 정보원

- 주문 정보

### Then

- 조회된 주문 사실을 근거로 주문 상태를 안내합니다.
- 안내한 상태가 어느 주문에 대한 것인지 알 수 있습니다.

### 금지 행동

- 조회하지 않은 주문 사실을 생성하지 않습니다.
- 문의에 필요하지 않은 배송 또는 취소 정책 사실을 사용하지 않습니다.

### 비규범적 예시

> order-003은 지금 어떤 상태인가요?

## 시나리오 2: 배송사 인계 전 배송 문의

### 목적

주문이 배송사에 인계되지 않은 경우 상세 배송 정보 없이 답변할 수 있는지 확인합니다.

### Given

- 고객 컨텍스트는 `customer-001`입니다.
- `order-001`은 `customer-001`의 주문입니다.
- `order-001`의 주문 상태는 `processing`입니다.
- `order-001`에는 Shipment가 없습니다.

### When

고객이 `order-001`의 배송 진행 상황을 문의합니다.

### 필요한 정보원

- 주문 정보

### Then

- 주문 상태를 근거로 아직 배송사에 인계되기 전임을 안내합니다.
- 문의에 답하기 위해 상세 배송 사실을 요구하지 않습니다.

### 금지 행동

- 존재하지 않는 택배사, 배송 상태, 위치 또는 배송 예정일을 생성하지 않습니다.
- Shipment 정보를 조회했다고 표현하지 않습니다.

### 비규범적 예시

> order-001은 아직 배송 시작 안 했나요?

## 시나리오 3: 배송사 인계 후 배송 문의

### 목적

주문 수준 정보와 배송사 수준 정보를 조건에 따라 사용하고 조합하는지 확인합니다.

### Given

- 고객 컨텍스트는 `customer-001`입니다.
- `order-002`는 `customer-001`의 주문입니다.
- `order-002`의 주문 상태는 `shipped`입니다.
- `order-002`의 Shipment 상태는 `out_for_delivery`입니다.

### When

고객이 `order-002`의 배송 진행 상황을 문의합니다.

### 필요한 정보원

- 주문 정보
- 배송 정보

### 규범적 Tool 선후관계

- `find_order`로 주문 상태를 확인한 뒤 `find_shipment`로 상세 배송 정보를 조회합니다.

### Then

- 조회된 주문 상태와 상세 배송 상태를 조합해 안내합니다.
- 쇼핑몰 관점의 주문 상태와 배송사 관점의 상세 배송 진행 상태를 구분합니다.

### 금지 행동

- `OrderStatus`만으로 상세 배송 상태를 추정하지 않습니다.
- 데이터에 없는 택배사, 위치, 운송장 또는 배송 예정일을 생성하지 않습니다.

### 비규범적 예시

> order-002는 지금 어디쯤 왔나요?

## 시나리오 4: 취소 가능한 주문

### 목적

현재 주문 상태와 canonical policy fact를 모두 근거로 취소 가능 여부를 안내하는지 확인합니다.

### Given

- 고객 컨텍스트는 `customer-001`입니다.
- `order-001`은 `customer-001`의 주문입니다.
- `order-001`의 주문 상태는 `processing`입니다.
- 취소 정책의 `cancellable_statuses`에는 `processing`이 포함됩니다.

### When

고객이 `order-001`의 취소 가능 여부를 문의합니다.

### 필요한 정보원

- 주문 정보
- 취소 정책

### Then

- 주문이 취소 가능한 상태임을 안내합니다.
- 현재 주문 상태와 정책을 답변 근거로 사용합니다.

### 금지 행동

- 주문을 실제로 취소하거나 변경하지 않습니다.
- 취소 요청을 접수했거나 완료했다고 약속하지 않습니다.

### 비규범적 예시

> order-001을 취소할 수 있나요?

## 시나리오 5: 취소 불가능한 주문

### 목적

정책에 없는 상세 사유를 만들지 않고 취소 불가 여부를 근거 있게 안내하는지 확인합니다.

### Given

- 고객 컨텍스트는 `customer-001`입니다.
- `order-002`는 `customer-001`의 주문입니다.
- `order-002`의 주문 상태는 `shipped`입니다.
- 취소 정책의 `cancellable_statuses`에는 `processing`만 포함됩니다.

### When

고객이 `order-002`의 취소 가능 여부를 문의합니다.

### 필요한 정보원

- 주문 정보
- 취소 정책

### Then

- 현재 정책상 주문을 취소할 수 없음을 안내합니다.
- 현재 주문 상태와 정책을 답변 근거로 사용합니다.

### 금지 행동

- 정책에 없는 상세한 취소 불가 사유를 생성하지 않습니다.
- 주문을 실제로 취소하거나 변경하지 않습니다.

### 비규범적 예시

> order-002를 취소할 수 있는지 알려주세요.

## 시나리오 6: 주문 식별 정보 없음

### 목적

고객이 주문을 식별하지 않은 **missing information** 상황을 처리하는지 확인합니다.

### Given

- 고객 컨텍스트는 `customer-001`입니다.
- `customer-001`은 `order-001`, `order-002`, `order-003`을 소유합니다.
- 후보 선택에 사용할 수 있는 canonical fact는 각 주문의 `order_id`와 주문 상태입니다.

### When

고객이 특정 주문을 식별하지 않고 주문 관련 요청을 합니다.

### 필요한 정보원

- 현재 고객의 주문 후보

### Then

- 현재 canonical fact로 검증할 수 있는 주문 후보를 제시합니다.
- 고객에게 처리할 주문을 선택하도록 요청합니다.

### 금지 행동

- 주문 하나를 임의로 선택하지 않습니다.
- 데이터에 없는 상품 요약, 주문 시각 또는 다른 식별 정보를 생성하지 않습니다.

### 비규범적 예시

> 제 주문은 지금 어디에 있나요?

## 시나리오 7: 지원하지 않는 정보로 주문 지칭

### 목적

식별 정보처럼 보이지만 현재 domain fact로 검증할 수 없는 **unsupported qualifier**를 처리하는지 확인합니다.

### Given

- 고객 컨텍스트는 `customer-001`입니다.
- `customer-001`은 `order-001`, `order-002`, `order-003`을 소유합니다.
- domain에는 상품 요약과 주문 시각이 없습니다.

### When

고객이 상품 설명이나 최근 주문 여부처럼 지원하지 않는 정보로 주문을 지칭합니다.

### 필요한 정보원

- 현재 고객의 주문 후보

### Then

- 현재 사실만으로 해당 표현을 이용해 주문을 식별할 수 없으므로 확인이 필요함을 나타냅니다.
- 검증할 수 있는 주문 후보를 제시하고 처리할 주문을 선택하도록 요청합니다.

### 금지 행동

- domain에 없는 상품 또는 최근 주문 정보를 확인한 것처럼 표현하지 않습니다.
- 지원하지 않는 표현을 근거로 주문을 선택하지 않습니다.

### 비규범적 예시

> 최근 주문은 지금 어떻게 되고 있나요?

> 티셔츠 주문을 취소할 수 있나요?

## 시나리오 8: 존재하지 않거나 다른 고객이 소유한 주문

### 목적

조회할 수 없는 주문을 처리할 때 다른 고객의 주문 존재 여부를 노출하지 않는지 확인합니다.

### Given

- 고객 컨텍스트는 `customer-001`입니다.
- 첫 번째 입력은 존재하지 않는 `order_id`를 사용합니다.
- 두 번째 입력은 `customer-002`가 소유한 `order-004`를 사용합니다.

### When

고객이 `customer-001` 컨텍스트에서 두 주문 중 하나를 요청합니다.

### 필요한 정보원

- 현재 고객 컨텍스트로 제한된 주문 정보

### Then

- 두 입력 모두 외부에 안전한 주문 조회 불가 결과로 처리합니다.
- 관찰 가능한 결과를 통해 `order-004`가 다른 고객에게 존재한다는 사실을 알아낼 수 없습니다.

### 금지 행동

- `order-004`의 사실을 `customer-001`에게 반환하지 않습니다.
- 요청한 주문이 다른 고객의 주문이라고 말하거나 암시하지 않습니다.

### 비규범적 예시

> order-999를 조회해주세요.

> order-004를 조회해주세요.

정확한 Python 오류 객체, 오류 코드, schema 및 메시지가 같아야 하는 것은 아닙니다. 호출자가 관찰 가능한 결과만으로 다른 고객의 주문 존재 여부를 알아낼 수 없어야 한다는 것이 계약입니다.

## 시나리오 9: 주문 조회 후 배송 정보원 실행 실패

### 목적

필수 후속 정보원의 실행이 실패했을 때 이미 확인한 사실과 확인하지 못한 사실을 구분하는지 확인합니다.

### Given

- 고객 컨텍스트는 `customer-001`입니다.
- `order-002`는 `customer-001`의 주문입니다.
- 주문 정보 조회는 성공하여 주문 상태 `shipped`를 반환합니다.
- 후속 배송 정보 조회는 실패합니다.

### When

고객이 `order-002`의 배송 진행 상황을 문의합니다.

### 필요한 정보원

- 주문 정보
- 실행 실패가 주입된 배송 정보

### 규범적 Tool 선후관계

- `find_order`로 주문 상태를 확인한 뒤 `find_shipment`로 상세 배송 정보 조회를 시도합니다.

### Then

- 이미 확인한 주문 상태 `shipped`는 안내할 수 있습니다.
- 상세 배송 진행 상태는 확인할 수 없다고 명확히 밝힙니다.

### 금지 행동

- 배송 정보 조회가 실패했는데 Shipment가 `out_for_delivery`라고 말하지 않습니다.
- 누락된 결과를 택배사, 위치 또는 배송 예정일 같은 생성된 사실로 채우지 않습니다.

### 비규범적 예시

> order-002는 지금 어디쯤 왔나요?

실패는 특별한 fake data 레코드로 표현하지 않습니다.

## 재검토 조건

구현된 시나리오에서 구체적인 필요가 확인될 때만 다음 가정을 재검토합니다.

- 모델이나 사용자가 `processing`을 반복적으로 오해합니다.
- 하나의 배송사 인계 전 상태로 필요한 고객지원 또는 정책 분기를 표현할 수 없습니다.
- `out_for_delivery` 이외의 상세 배송 상태가 필요한 행동 분기가 생깁니다.
- 같은 상태의 복수 주문을 현재 canonical fact만으로 구분할 수 없습니다.
- canonical fixture로 새로운 필수 Agent 행동을 재현할 수 없습니다.
- 실제 쓰기 동작으로 인해 서버 측의 결정적인 정책 집행이 필요해집니다.
